# راهنمای به‌روزرسانی سامانه (Update & Rollback)

این سند نحوهٔ **به‌روزرسانی امن رفرال‌بات** در هاست اشتراکی یا سرور اختصاصی، **بازگردانی (Rollback)** در صورت بروز خطا، و **ساخت بستهٔ رسمی انتشار** را توضیح می‌دهد.

---

## ۱) دسترسی و پیش‌نیازها

- بخش **پنل مدیریت → سیستم → به‌روزرسانی** (`/admin/update`) **فقط برای «مدیر کل» (`superadmin`)** در منو نمایش داده می‌شود و تمام مسیرهای آن برای سایر نقش‌ها با کد `403` مسدود است.
- **افزونهٔ `ZipArchive` (`php-zip`)**: برای استخراج بسته و ساخت پشتیبان فایل‌ها الزامی است (در cPanel / DirectAdmin از بخش *Select PHP Version → Extensions → zip* فعال می‌شود).
- **دسترسی نوشتن**: پوشهٔ `storage/` (برای پشتیبان و فایل‌های موقت) و پوشه‌های کد برنامه باید توسط کاربر PHP قابل نوشتن باشند.
- **cURL + OpenSSL**: برای بررسی و دانلود مستقیم از GitHub لازم است. اگر هاست دسترسی خروجی به `github.com` را محدود کرده باشد، **روش نصب دستی با آپلود فایل ZIP** بدون هیچ ارتباط خارجی کار می‌کند.

---

## ۲) چه چیزهایی به‌روز می‌شوند و چه چیزهایی هرگز لمس نمی‌شوند؟

### مسیرهای مجاز (`UpdateService::ALLOWED_PATHS`)
فقط و فقط مسیرهای زیر از بستهٔ به‌روزرسانی کپی می‌شوند:

```
src/
views/
public/
bin/
docs/
database/migrations/
install.php
index.php
VERSION
README.md
```

از آنجا که `VERSION` در فهرست سفید قرار دارد، بلافاصله پس از نصب موفق شمارهٔ نسخهٔ سرور به‌روز می‌شود و سامانه وارد حلقهٔ «نسخهٔ جدید موجود است» نمی‌شود.

### مسیرهای کاملاً محافظت‌شده (هرگز بازنویسی یا حذف نمی‌شوند)
- فایل **`.env`** و تمام گونه‌های آن (`.env.local`، `.env.production` و...) — رمز پایگاه داده و کلید رمزنگاری `APP_KEY` کاملاً امن می‌مانند.
- پوشهٔ **`storage/`** — فایل قفل نصب (`installed.lock`)، کلید برنامه (`app_key.php`)، پشتیبان‌ها، آپلودها و لاگ‌ها هرگز دست نمی‌خورند.
- پوشه‌های **`.git/`**، **`.github/`**، **`vendor/`** و **`node_modules/`**.
- **داده‌های پایگاه داده** (کاربران، کیف پول‌ها، تراکنش‌ها، برداشت‌ها، تنظیمات و توکن ربات) حفظ می‌شوند و فقط Migrationهای جدیدِ اجرانشده اعمال می‌گردند.

## ۳) دو روش به‌روزرسانی از پنل مدیریت

### روش اول — به‌روزرسانی خودکار از GitHub Releases
1. وارد **پنل مدیریت → به‌روزرسانی** شوید.
2. روی دکمهٔ **«بررسی نسخه جدید»** کلیک کنید.
3. اگر نسخهٔ جدیدتری از نسخهٔ فعلی (`VERSION`) منتشر شده باشد، شمارهٔ نسخه، یادداشت تغییرات (Release Notes) و حجم بسته نمایش داده می‌شود.
4. روی **«دانلود و نصب نسخه vX.Y.Z»** کلیک و تأیید کنید.
5. سامانه به‌ترتیب این مراحل را خودکار انجام می‌دهد:
   - دریافت فایل ZIP رسمی از دامنهٔ مجاز GitHub روی HTTPS (با بررسی گواهی SSL)
   - تطبیق هش `.sha256` آرشیو (در صورت پیوست بودن به Release)
   - استخراج امن و اعتبارسنجی `VERSION`، `update.json` و `CHECKSUMS.sha256`
   - تهیهٔ پشتیبان SQL از تمام جداول دیتابیس (شامل جدول `migrations`) در `storage/backups/`
   - تهیهٔ پشتیبان ZIP از فایل‌های فعلی (`pre-update-files-vX.Y.Z-*.zip`) در `storage/backups/`
   - جایگزینی اتمیک فایل‌ها و اجرای Migrationهای جدید
   - بازنشانی OPcache و پاک‌سازی پوشهٔ کاری موقت (`storage/updates/work/`)

> **بررسی خودکار روزانه:** با فعال کردن گزینهٔ «بررسی خودکار روزانه نسخهٔ جدید» در کارت تنظیمات، حداکثر هر ۲۴ ساعت یک بار هنگام ورود مدیر کل به داشبورد وجود نسخهٔ تازه بررسی و در کنار منوی «به‌روزرسانی» نشان‌گذاری می‌شود. **نصب هرگز بدون تأیید دستی شما انجام نمی‌شود.**

### روش دوم — آپلود دستی بستهٔ ZIP (آفلاین / هاست محدود)
1. فایل رسمی `refrallbot-update-vX.Y.Z.zip` را از صفحهٔ Releases گیت‌هاب روی رایانه یا گوشی دانلود کنید.
2. در **پنل مدیریت → به‌روزرسانی → نصب دستی با آپلود فایل ZIP** فایل را انتخاب و روی **«آپلود و نصب بسته»** بزنید.
3. دقیقاً همان زنجیرهٔ بررسی امنیتی، پشتیبان‌گیری خودکار، کپی فایل‌ها و اجرای Migration اجرا می‌شود.

> توجه: دانلود معمولی «Source code (zip)» گیت‌هاب فاقد فایل `CHECKSUMS.sha256` است و به‌دلایل امنیتی رد می‌شود. همیشه فایل پیوست‌شدهٔ `refrallbot-update-vX.Y.Z.zip` را دانلود کنید.

## ۴) کنترل‌های امنیتی بسته

| تهدید | سازوکار دفاعی در `UpdateService` |
|---|---|
| بستهٔ جعلی یا ناقص | اجباری بودن `CHECKSUMS.sha256` و تطبیق SHA-256 تک‌تک فایل‌ها با `hash_equals` + رد هر فایل ثبت‌نشده در فهرست هش |
| حملهٔ Zip Slip (`../../`) | بازرسی تمام مسیرهای ZIP پیش از استخراج، رد `..`، بک‌اسلش پیمایشی، مسیر مطلق و بررسی `realpath` |
| حملهٔ Symlink | تشخیص بیت نوع فایل یونیکس (`0120000`) در هدر ZIP و رد پیوندهای نمادین در مبدأ و مقصد |
| حملهٔ Zip Bomb | محدودیت حجم بسته (۵۰ مگابایت)، حجم بازشده (۱۲۰ مگابایت)، تعداد فایل (۵۰۰۰) و نسبت فشرده‌سازی |
| بازنویسی `.env` یا `storage/` | مسدودسازی در دو لایهٔ مستقل (`validatePackage` و `copyFiles`) با حفظ دقیق نقطهٔ ابتدای نام فایل |
| نصب نسخهٔ قدیمی‌تر (Downgrade) | مقایسهٔ `version_compare` با نسخهٔ فعلی و رد نسخه‌های قدیمی‌تر |
| حملهٔ SSRF در دانلود | محدودسازی دانلود به HTTPS و دامنه‌های رسمی GitHub (`github.com`, `api.github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`, `codeload.github.com`) |
| اجرای هم‌زمان دو آپدیت | قفل انحصاری `flock` روی `storage/updates/work/update.lock` |

## ۵) بازگردانی خودکار و دستی (Rollback)

- **بازگردانی خودکار:** اگر در میانهٔ کپی فایل‌ها (مثلاً کمبود فضا یا مجوز فایل) یا در حین اجرای Migration خطایی رخ دهد، سامانه **به‌صورت خودکار** تمام فایل‌های قبلی را از پشتیبان تازه ساخته‌شده بازمی‌گرداند، فایل‌های نیمه‌اضافه‌شده را پاک می‌کند و رویداد را در تاریخچه ثبت می‌نماید.
- **بازگردانی دستی فایل‌ها:** از جدول «بازگردانی فایل‌ها» در پایین صفحهٔ `/admin/update` می‌توانید هر یک از پشتیبان‌های `pre-update-files-*.zip` را با یک کلیک بازگردانی کنید (`.env` و `storage/` دست‌نخورده می‌مانند).
- **بازگردانی پایگاه داده:** پشتیبان‌های SQL پیش از به‌روزرسانی با پیشوند `pre-update-db-v*` در `storage/backups/` ذخیره می‌شوند و از صفحهٔ **پشتیبان‌گیری** (`/admin/backup`) قابل دانلود و ایمپورت در phpMyAdmin یا خط فرمان هستند. جدول `migrations` نیز در این پشتیبان وجود دارد تا پس از بازیابی، خطای `table already exists` رخ ندهد.

---

## ۶) ساخت و انتشار نسخهٔ جدید (ویژهٔ توسعه‌دهنده)

۱) شمارهٔ نسخه را در فایل `VERSION` ریشهٔ پروژه به‌روز کنید (مثلاً `1.2.0`) و تغییرات را کامیت کنید.

۲) اسکریپت ساخت بستهٔ رسمی را اجرا کنید:

```bash
php bin/build-update.php
# یا با تعیین نسخه و مسیر دلخواه:
php bin/build-update.php --version=1.2.0 --out=/tmp/refrallbot-update-v1.2.0.zip
```

خروجی دو فایل خواهد بود:
- `refrallbot-update-v1.2.0.zip` (حاوی فایل‌های مجاز + `VERSION` + `update.json` + `CHECKSUMS.sha256`)
- `refrallbot-update-v1.2.0.zip.sha256` (چک‌سام SHA-256 کل آرشیو)

۳) در گیت‌هاب یک **Release** جدید با تگ `v1.2.0` بسازید و **هر دو فایل** بالا را در بخش *Assets* پیوست و منتشر کنید.

## ۷) عیب‌یابی خطاهای رایج

| پیام خطا | علت و راه‌حل |
|---|---|
| `افزونه ZipArchive در PHP فعال نیست` | از کنترل‌پنل هاست افزونهٔ `zip` را برای نسخهٔ PHP فعال کنید. |
| `حجم فایل ZIP از سقف مجاز آپلود PHP بیشتر است` | مقدار `upload_max_filesize` و `post_max_size` را در تنظیمات PHP هاست افزایش دهید (مثلاً `32M`). |
| `بسته فاقد فایل CHECKSUMS.sha256 است` | به‌جای Source code پیش‌فرض گیت‌هاب، فایل رسمی `refrallbot-update-vX.Y.Z.zip` را آپلود کنید. |
| `محدودیت نرخ درخواست GitHub API` | چند دقیقه صبر کنید، یا یک Personal Access Token فقط-خواندنی در تنظیمات به‌روزرسانی ثبت کنید، یا از آپلود ZIP استفاده نمایید. |
| `نوشتن فایل ممکن نشد` | مجوز پوشه‌های پروژه (`0755` برای پوشه‌ها و `0644` برای فایل‌ها) و فضای خالی هاست را بررسی کنید. |
